# Design

How several AI agents work on one Unity project at once, and how their work gets back together. The research behind each choice is in [`research/`](research/).

## The flow

1. **Claim.** A task declares the scenes, prefabs and assets it will write before it starts. If its claim overlaps a running task's claim, the task is refused. Shared registries become one file per feature, so two features never have to write the same list. Code: [`src/upe/claims.py`](src/upe/claims.py). A claim lists files, folders (ending `/`) or globs; claiming an asset claims its `.meta`. Two globs that cannot be shown apart count as overlapping. At merge time, any changed file outside the branch's claim stops the merge before the council.
2. **Isolate.** The task gets a git worktree from a pool of slots (`<root>/slots/s1`, `s2`, ...). A finished task's slot is parked, detached and clean with its `Library` kept, and the next task or merge candidate checks out its own branch there. Unity has seen that path, so it imports only the difference: about 20 s plus the changes, against about 200 s for a Library at a new path ([05](research/05-measurements.md)). A new slot is made only when every slot is busy, and its `Library` is copied from a warm golden copy, never linked: symlinking `Library` corrupts it ([02](research/02-unity-cli.md)). It gets its own Editor, addressed by project path through the `unity` CLI. Code: [`src/upe/workspace.py`](src/upe/workspace.py). Branches are named `upe/<task-id>`. The golden Library is not copied while its Editor is open, and a slot with uncommitted work or an open Editor is never parked or reused. Who holds which slot is kept in `<root>/.upe/slots.json`, changed under a file lock. Git-ignored files the project needs to compile (a third-party package kept out of git, for example) are listed in `local_copies` and copied from the main checkout into every worktree, candidate and golden; a worktree without them stops on compile errors ([05](research/05-measurements.md)).
3. **Merge in layers.**
   1. Plain git merge.
   2. For same-file `.unity`, `.prefab` and `.meta` conflicts, UnityYAMLMerge runs headless with `-p --fallback none`, so a failure is an exit code and one side is never picked silently.
   3. `packages-lock.json` is deleted and regenerated. `manifest.json` merges by key. ProjectSettings lists merge as a union.
   4. If two changes truly collide, the task's builder is re-run on the merged project instead of hand-editing YAML. Builders are written to be safe to run twice.

   Code: [`src/upe/merge.py`](src/upe/merge.py). The merge runs on a candidate branch `upe-merge/<task-id>` in its own worktree; the target moves only at step 6, by fast-forward, and only if it has not moved since. A `.meta` whose GUID differs between the two sides is refused, never merged. The ProjectSettings union ([`src/upe/project_settings.py`](src/upe/project_settings.py)) covers `TagManager.asset` and `EditorBuildSettings.asset`. Tags merge as a set. Layers are 32 numbered slots that scenes and prefabs store by number, so the same slot changed differently on both sides stops the merge. Build scenes are keyed by GUID; the target's order is kept and the branch's new scenes go after it, since the order is the build index. If anything else in those files changed on both sides, the merge stops.
4. **Check.** The merged result is re-parsed as YAML, its fileIDs and GUIDs are checked, and a batch Unity run looks for missing references. Then `unity test --mode EditMode` compiles it and runs the EditMode tests in an Editor of its own, so the project must not be open at that moment. Each failed test is a finding unless it also fails on the target before the merge. Code: [`src/upe/checks.py`](src/upe/checks.py). The static checks also catch leftover conflict markers, assets and folders without a `.meta`, orphan `.meta` files, a folder's `.meta` (`folderAsset: yes`) over a file or a file's over a folder, GUIDs used twice, and Transforms whose `m_Father` and `m_Children` disagree. The `.meta` rules read the merge's commit through git (`ls-tree` and two `git grep`s that read every file as text with fixed output options, so neither git's attributes, the user's grep or colour settings, nor git's pathspec variables change them; never the slot's files: a slot Unity opened and a scrubbed one give one answer; a tracked `.meta` with no GUID is a finding), take a folder `.meta` with nothing tracked under it as an empty folder, and report only what the target's commit does not already give. GUID references are checked against the commit's tracked `.meta` files and the package cache, and only when `Library/PackageCache` exists, since package GUIDs live there. A batch Editor with a graphics device (without `-nographics` Unity crashes loading a scene with a Terrain) then loads each changed scene and prefab and reports missing scripts, missing prefabs and dangling object references (`Upe.Agent.SceneCheck.Run` in [`unity/com.upe.agent`](unity/com.upe.agent)); problems already on the target before the merge are noted, not counted.
5. **Council.** The merge council (below) says GO or NO-GO, through `upe verdict`.
6. **Land.** Only a GO from the council lands the merge.

UnityYAMLMerge's exit code does not prove both sides were kept: it can exit 0 having dropped a rename on an object the other side deleted. So the tool compares its result with both sides, object by object, and stops if a change one side made is missing, an object was deleted on one side and changed on the other, an object neither side changed differs in the result, or the result has an object neither side has. Quotes around a whole value or a key, and where a long value is folded onto more lines (only a line that continues a value is joined, never a new key or list item), are formatting (UnityYAMLMerge folds long references and names at another column than the Editor, and drops quotes the Editor wrote); a space inside quotes is part of the value. Tried on every scene and 150 prefabs of the test project, each side adding an object: none stops. In an object both sides changed it counts lines: each side's added and removed lines must be in the merged object, a line one side added and the other removed stops the merge, and so does a side's new order of lines (children, components) missing from the result. The `--- !u!` line counts, so a dropped `stripped` flag is a loss. Order is compared pair by pair, so a reorder on each side of one object can both be kept. Edits apart from each other are also checked by place: a line merge of the object predicts the result there exactly, and only where the two sides' edits overlap or touch may UnityYAMLMerge combine them its own way. A line one side moved and the other removed or rewrote stops the merge. What is left is close edits among repeated lines: where the two sides' edits touch, a line found more than once in the object is only counted, not placed. `.meta` files rest on UnityYAMLMerge alone ([05](research/05-measurements.md), "Merging real files"). `land` tries the merge before the long baseline, so a conflict is found in seconds.

A semantic merger of our own for scenes and prefabs comes later, and only if conflicts stay common after steps 1 to 5.

**Running it.** [`src/upe/flow.py`](src/upe/flow.py) chains the steps; `python -m upe` is its command line (see the README). `start` does steps 1 and 2. `land` does steps 3 to 6, in this order:

1. Give the candidate a slot at the target, the same way a task gets one. Record the scene problems already on the target, as the scene check of step 4 will need them, judged on the branch's changes: a branch that changes scenes or prefabs checks those the target has (a scene the branch adds is not on the target, and is not given to the run, which would throw on it); one that deletes a scene or prefab, or changes no scene and fails the allow list of step 4, needs every scene and prefab of the target: the result kept for the target's commit in this slot (`<root>/.upe/scene-baselines/<commit>.<slot>.json`, which names the id of the slot's `Library` as made, and is read only by that `Library`: a slot removed and made again under its name has the golden's copy, and a new id. One commit's full check gave other problems in another slot: one commit of the test project gave about 1,100 in one slot and about 50 more in another, why is not known (some are under the git-ignored local copies an acquire puts back, and the two runs were 8 hours apart, so the slot is not told from the time); so a result made in one slot is never read in another), else a full run here, under the lock of the commit and the slot (`scene-baselines/<commit>.<slot>.lock`, a guard: a slot has one owner at a time, so no land waits on it, and its wait, up to 75 minutes then exit 2, is not in a land's bound), kept for the commit and the slot when it is complete (a report written by this run, no `exception` row, no licensing failure or compile error in its log, exit 0 or 1, and at least one scene or prefab loaded); one the allow list passes needs none. `checks.md` says which way the scene baseline was found: kept, this land's full run, this land's check of the changed paths, or none. Then look up the target's tests. A full EditMode result kept for the target's commit (`<root>/.upe/test-baselines/<commit>.json`): nothing runs on the target. Else a kept full result of the nearest ancestor of the target, in the new format: no tests run on the target before the merge, and step 4 runs there only the classes of the tests that fail on the merge. Else the full suite runs on the target here, as before, and its result is kept for the commit, so the tests run on a target commit once. A kept result keeps apart the tests that failed on every attempt, the flaky ones (failed, then passed), and the unconfirmed ones (failed, never seen failing twice); a file in the old format, one list of every test that failed even once, serves only its own commit. On the test project one full run took 14 to 15 minutes on a 16 GB machine, most of it starting and compiling the Editor.
2. Merge the branch.
3. Take the tool's packages out of the merged manifest if the branch committed them. Regenerate the lock with a plain batch Editor run if the manifest changed, then scrub it. Re-run builders.
4. Run the static checks, then the scene check and the Unity compile and tests. The council never sees a merge that fails here. **When the full scene check runs**, judged again on what the merge changes against the target, after the builders: a merge that changes scenes or prefabs checks those paths, as before, also when it changes code too (open, by design: a scene plus an `.asmdef` or an Editor script leaves the other scenes unloaded); one that deletes or renames a scene or prefab checks every one (what referred to it is elsewhere). One that changes no scene or prefab checks every one, unless every path it changes is added (no rename detection: a rename is a delete and an add), under `Assets/`, and is on the allow list: a passive asset (textures, audio, video, fonts, models, materials, `.asset`, animations and controllers, text and data files), whose new GUID nothing existing refers to; a `.meta` paired with an asset or folder the merge adds, with one `guid` line, whose GUID no other `.meta` and no asset of the package cache has, and no file of the target names (an asset deleted while a scene still names it, brought back with its old `.meta`, keeps the full check); or a `.cs` inside a test assembly the target already has (an `.asmdef`, not an `.asmref`, with `UNITY_INCLUDE_TESTS`, `TestAssemblies` or a test runner reference by name) whose text names no hook a scan sees (the import and load hooks, `AssetsModifiedProcessor`, `partial`, `OnValidate`, `ExecuteAlways`, and `ScriptableObject`, `OnEnable`, `Awake` and the serialization callbacks (`ISerializationCallbackReceiver`), which run when an instance the merge adds is imported, after removing formatting characters; a `\u` escape counts as one; a script that does not read keeps the full check). Then the scene check is skipped and `checks.md` and the brief say so and why. Everything else (an `.asmdef`, `.asmref`, `.rsp`, plugin, shader, anything under `Packages/` or `ProjectSettings/`, any other script, a change or a delete) checks every scene and prefab, with the reasons in `checks.md`. **Open, by design:** a class that derives from a hook through a base class of the project, or of a precompiled `.dll`, which a text scan cannot see; an existing hook of the target (an `AssetPostprocessor`) that reacts to an added file by changing other assets; and existing code of the target that runs when an added file (an `.asset`, `.controller` or `.playable`) loads an instance of a class the target has (`OnEnable`, `Awake`, `OnValidate`, the serialization callbacks, constructors and field initializers, of a `ScriptableObject`, a `StateMachineBehaviour` or a playable, and of a `[SerializeReference]` type it names) and changes other assets. `checks.md` names each whenever a skip relies on it, with how many of the target's scripts name a hook, or, at least, `ScriptableObject`, `StateMachineBehaviour`, `PlayableAsset` or `TrackAsset` (a class derived through a base class of the project is not counted). When the judgment after the merge needs another scene baseline than the one step 1 made, it runs then, on the target, in the candidate's own slot checked out at the target, and the candidate goes back on its branch at the merge (one slot for the baseline and the merge's check, as in step 1). **A kept full result exists** after a land whose merge ran the full check and passed its checks (kept for the merge's commit, which is the target's once it lands, and the candidate's slot and its `Library`), or after a full run on that commit in step 1, in that slot; only a land that needs the target's whole baseline, and whose candidate is in that slot, reads it (a land that checks paths runs its own check of them). So it saves the target's full check only on a target a land of this tool made with a full check, or one a land has already checked in full, and only when the land's candidate takes that slot: a slot is the lowest-numbered one parked, not the one that holds a result (in trial runs, neither of the two lands on a commit checked in full took the slot that checked it). The CLI's retry does not re-run parameterised tests, yet lists them as failed: the tool runs the classes of the failed tests it did not retry once more, with no retry, under a report of its own (`.rerun.xml`), after every full run whose result is kept (the merge's, and the target's). A test that fails again failed on every attempt; one that passes is flaky and does not stop the land. A test that still fails is known only by the target's own kept result, or, with an ancestor's result, when it fails in a run of only its class on the target and the ancestor's result lists it as failed on every attempt. That run is in a slot of its own, detached at the target and owned by `base:<task>`, so nothing the merge's run left in the candidate is in it (the Library of a parked slot is an earlier task's, as the candidate's is). A test that passes alone there, or is not there (a class the branch added), is new at once; one that fails alone that the ancestor's result does not list as failed on every attempt (flaky there, unconfirmed, or absent: a class renamed since) sends the land to the full suite on the target, in that slot, kept for its commit. A class-only result is never written as a commit's result; it goes to `runs/<task>/target-classes/`. `checks.md` says how each known test was decided. **Open, by design:** the re-run runs a parameterised test's class alone, so a test the branch breaks only in the full suite's order passes there, is flaky, and lands, where the target's full run would have stopped it; the CLI's own retry does the same for other tests. And a test that failed in the ancestor's full run on every attempt, was fixed on the target since by commits the tool did not check, fails when its class runs alone, and is broken again by the branch, is taken as known; and, kept as failed in the merge's result, it is known to the next land too. `checks.md` names this case, and how many commits before the target the ancestor is, each time a class-only run decides a test.
5. `land` writes the council brief and stops. The council sits, and the second `upe verdict` acts on the votes: two GOs land by fast-forward, two NO-GOs throw the candidate away and keep the claim, and a split keeps the candidate until the user runs `decide`.

The claim is released only when the task lands or is finished. The records of each run go in `<root>/.upe/runs/<task>/`. `land` runs one task; two tasks landing at the same moment are kept safe by the fast-forward check (the second is told to land again), not by a queue. A target that moves during a land's Unity runs stops that try with nothing landed, and when one of the tool's own lands moved it forward, `land` starts again on the new target by itself, up to three times (a move backwards or to any other commit, which branch code run by Unity could make, stops for a person to look; a land records its commit just after moving the target, so the check waits a few seconds for that record); when another task's land moved it, that land's merged test run is the new target's baseline, so the next try skips those tests. The golden Library is a worktree of its own that the tool makes (`golden --create`) and nobody works in. `golden` moves it to the target by force and lets a batch Editor import the difference. It runs after every land (`refresh_golden_after_land`, on by default): at the same path a reopen costs about 20 s plus the import of what changed. A checkout the tool did not make is never moved. A task started from a newer commit than the golden notes it: Unity imports the difference in the task's own Editor.

## The merge council

Two agents decide whether a merge goes forward. The tool calls no model (decision 11): the members are agents from the user's own apps, each in a fresh session of its own. Preferably they are two different models, for example one Opus 5.5 and one Sonnet 5.5. Each is started at medium effort (decision 12).

**Neither did the work.** Code: [`src/upe/council.py`](src/upe/council.py). When the checks pass, `land` writes `council-brief.md` into the task's run folder: the rules below, the path of the merged worktree, how to answer, and the evidence. The task waits in `awaiting-council`. Each member reads the brief and the worktree with its own tools, changes nothing, and records its verdict as JSON with `upe verdict <task> --member <name> --file <verdict.json>`. The second verdict decides. Neither may be an agent that wrote either branch, planned the task or resolved a conflict in this merge, and neither may read the other's verdict first. The tool cannot see who an agent is, so these rules are the members' to keep: the brief states them, a member name can vote only once, and a NO-GO without a finding that names a file is refused. Running `land` again throws the old verdicts away.

**When it sits:** after the automated check in step 4 passes. A merge that fails to compile or loses a reference never reaches the council.

**What each member gets:**
- the task briefs and the claims of both branches
- the diff of each branch against the merge base, and the diff of the merged result
- every conflict and how it was resolved (git, UnityYAMLMerge, builder replay), and for a conflict the agent resolved on its branch, each file that merge decided (one two or more parents changed, or one that is not the version a plain merge gives) against each parent, so a side the resolution dropped shows. These are plain diffs: no merge is run again, so no merge driver or signature program from git config runs
- the check results from step 4
- read-only access to the merged worktree, to open any file it wants

Members get the evidence, not anyone's conclusion about it.

**How it votes:**
- The two members review **independently**. Neither sees the other's verdict before giving its own.
- Each returns a verdict: `GO` or `NO-GO`, with findings that name a file, and for a NO-GO what would change its mind.
- **Both GO:** the merge lands.
- **Both NO-GO:** the merge is refused. Their findings go back to the task.
- **Split:** the user decides, with both verdicts in front of them.

**What it checks:**
- Both sides' changes are still there after the merge. Nothing was dropped in a resolution.
- No change from one branch breaks the other's feature.
- Scene and prefab references still point where they should.
- The merge contains only what the briefs asked for, with nothing extra.

## How agents use it

Code: [`src/upe/__main__.py`](src/upe/__main__.py), and the skill in [`skill/upe/SKILL.md`](skill/upe/SKILL.md).

- **The skill.** `upe skill --to ~/.claude/skills --to ~/.codex/skills` installs it into each app, with this machine's command filled in. It says when to use the tool, the working steps, the rules, and how to sit on a council.
- **The command.** Agents run the `upe` console script (`.venv/Scripts/upe.exe`) or `python -I -m upe`, never `python -m upe` from a worktree. The config comes from `UPE_CONFIG` or the tool's own folder, never the current folder, and a config inside the project, the root or the golden is refused.
- **Output.** `--json` prints one JSON object; errors go to stderr as `{"error": ...}` with exit 2.
- **Long runs.** `--detach` starts the command in a background process at the same priority and prints a job id; `upe job <id>` gives its state, its current `stage`, its exit code and the end of its log, and `--wait` blocks until it is done, 9 minutes at most per call. Records are in `<root>/.upe/jobs/`. The detached child runs `python -I -m upe`, which ignores `PYTHONPATH`, so `--detach` works only with the tool installed (`pip install -e .`): run from a checkout with `PYTHONPATH=src`, the child ends with exit 3, "No module named upe".
- **The Editor.** `upe editor open|close|status <task>`, `upe editor test <task> [--filter]` (EditMode, in its own Editor), and `upe editor run <task> <Class.Method>` (one batch Editor, then quit). Each works only in the task's own slot. `editor test` declares `testing` to the judge for its length. After `test` and `run`, the tool puts back tracked files the run changed outside the claim and lists the files it made.

## Security

Every agent runs as the user, on the user's machine, with the user's rights (decision 15). The review behind this list, finding by finding, is [06](research/06-security.md); each item here is in the code.

**Landing only what was checked and reviewed.**
- The target comes from the config, never from the run records, which any agent can write. `merge.json` naming another branch lands nothing.
- The landed commit must still be the candidate branch's tip, and the task branch's tip must be inside it.
- A target that tracks a remote is refused (it could reach `origin`), and so is a target checked out anywhere outside the tool's slots.
- A verdict must name the merged commit, so a vote on an earlier merge does not count. A new `land` voids the earlier merge and its votes as it starts, so one cut short leaves nothing open to votes.
- A verdict on a merge the target has moved past is refused and not recorded, since that merge can no longer fast-forward. `status` says so as soon as the target moves, and its next step is to land again, so the council and the agent stop spending time on a merge that cannot land.
- A verdict from the agent process that ran `land`, or from the same process as the other member, is refused ([`identity.py`](src/upe/identity.py)). That stops an agent voting on its own work, or through its own subagents.
- `upe decide` needs a person at a terminal, typing the task id.

**What a branch may change.** A change outside the claim, or to agent instructions, hooks or tooling (`checks.PROTECTED`: `.claude/`, `CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `.codex/`, `.cursor/`, `.vscode/`, `.github/`, `.gitattributes`, `.gitmodules`, `upe.toml`, plus `protected_paths`), stops the merge; a person lands those by hand. So does code in namespace `Upe.Agent`, which the checks call by name, and two paths that differ only in case.

**Branch code that the checks run.** The scene check and the tests load the branch's Editor code with the user's rights before any council sees it. That cannot be closed without running Unity as another user or in a sandbox. What is done:
- Tests that leave no results report count as not finished, whatever the exit code.
- The target's ref, the task's two branches, git config (all but `branch.*` tracking, which the user changes in passing; a remote's URL is kept, since it is where the next push goes) and hooks are fingerprinted around each Unity run on a candidate; a change fails the land. Regenerate and builder runs are guarded too, except the candidate's own ref, which the tool commits to then; a protected file or, with no builder, a file outside the claim that appears in the merge stops it. A target that moved says so without blaming the branch, since another task's land does that.
- A test report that lists no tests, or lists no failures after a failing exit, is not a pass.

**The council brief.** Everything from the agents (briefs, claims, diffs, the check log) is fenced with a fence longer than any backticks inside it, labelled as data, and followed by the rules again. A file list comes first, so a long diff cut short still shows every file. Members are told not to open a session in the merged worktree, whose own CLAUDE.md and hooks come from the branch.

**Slots and the shared `.git`.**
- The tool's git runs with no hooks, no fsmonitor and no symlinks, and its diffs with no external diff or textconv drivers ([`safegit.py`](src/upe/safegit.py)).
- Slot names must be `s<number>`. Nothing destructive (`reset --hard`, `clean`) runs outside a slot that git confirms is that worktree, and never in the main checkout.
- Copies refuse junctions and symlinks inside the tool's folders, since `robocopy /MIR` would delete through them.
- A reused slot loses its index flags, every ignored file but its Library, and its per-worktree git config, so nothing hidden from the dirty check reaches the next owner.

**State.** One `land`, `verdict`, `decide` or `finish` per task at a time. Locks are OS file locks, which the system drops when their holder dies. State files are written through a temporary file and a rename. Task ids are checked everywhere they name a file.

**Still open.** These need OS-level separation, or credentials agents do not hold:
- Any agent can run `git update-ref`, edit `.upe/`, or edit a forged test baseline itself.
- Branch code in a batch Editor can read the environment it inherits, including any keys the agent's app passes on.
- Any agent that can reach a stored git credential can push. Keep no GitHub credential where command-line git finds it.

## The tool's code inside a worktree

The project's repo is not changed for the tool (decision 7). Code: [`src/upe/agent_package.py`](src/upe/agent_package.py).

- `com.upe.agent` is copied into `Packages/` as an embedded package and listed in the repo's local `info/exclude`, so git never sees it.
- `com.unity.pipeline`, which the `unity` CLI needs, is added with `unity pipeline install`.
- `Packages/manifest.json` and `Packages/packages-lock.json` are then marked skip-worktree in that worktree's index, so these local edits are never committed. A task that really needs a package change claims `manifest.json`, and the tool lifts the mark on the manifest for it. That task's commits then carry the tool's `com.unity.pipeline` entry too; the merge takes it back out (`strip_tool_packages`) unless the target already has it. The lock stays marked, and is regenerated whenever the merged manifest differs from the target's.
- Unity's IDE integration writes `.vscode/settings.json` (`dotnet.defaultSolution` set to the folder's name) and a `<folder>.slnx` on every open. The settings file is marked skip-worktree too. The `.slnx` is excluded by name, `/<folder>.slnx`, because `info/exclude` is shared with the main checkout and a project may track `.slnx` files of its own.
- Whether a slot has uncommitted work is read from `git diff HEAD` and untracked files, not `git status`. With `core.autocrlf`, git calls a file Unity rewrote from CRLF to LF modified without comparing its content ([05](research/05-measurements.md)).
- After a merge, Unity regenerates `packages-lock.json` in a batch run before the tool's packages go in. `scrub_lock` is the safety net: it drops the tool's packages, and anything only they pulled in, from a lock about to be committed.

## The priority judge

The Editors share one machine, so they compete for RAM and CPU. The priority judge decides which session gets them. It is fixed rules, not an agent (decision 11).

- A session that needs its Editor heavily (rendering, PlayMode, lighting, builds) is given priority.
- Other sessions give way.

Code: [`src/upe/judge.py`](src/upe/judge.py); `python -m upe judge --watch` runs it.

- **What it reads.** Each session's declared activity: agents run `upe activity <task> <kind>` before and after heavy work, because only the agent knows it is about to render. It also reads every Unity process on the machine, with the project it has open, its memory and its CPU over two seconds. Import workers and shader compilers count with their Editor. Last, the machine's free memory and core count.
- **How it decides.** Each session gets `high`, `normal` or `low`, with a reason, by these rules:
  - A session doing heavy work (playmode, rendering, lighting, building) is high. At most `max_high` sessions are; among more, the one that declared first wins.
  - While a session is heavy, idle and background sessions (importing, compiling, testing) are low, and editing sessions normal.
  - With no heavy session, every session is normal. The exception is when memory is short: then idle sessions are low.

  It runs again whenever an activity changes, and every `judge_every_s` otherwise.
- **How it applies a decision.** It sets the Windows priority class of every process of the session. `normal` is `editor_priority`, BELOW_NORMAL by default; `high` is one class above it and `low` one below, so NORMAL, BELOW_NORMAL or IDLE. With `editor_priority = "normal"` they are ABOVE_NORMAL, NORMAL and BELOW_NORMAL. HIGH and REALTIME are never used. Memory is not capped, since a capped Editor crashes. Editors the user opened on other projects are reported and never touched.
- **Records.** Each decision and the snapshot it was made from are appended to `<root>/.upe/judge.jsonl`.
- **Numbers.** `max_high` is 1. Memory counts as short below `memory_short_mb` (4096 MB, one Editor's first-open peak). On a 16 GB machine, memory, not CPU, was the limit: three batch Editors filled it while the CPU averaged 43% ([05](research/05-measurements.md)). So CPU priority helps a session that renders or builds, but it does not free memory. On a 12-thread, 32 GB machine it is the reverse: three Editors fit in memory and take 90 to 97% of the CPU, so priority is the lever that counts there. Whether batch runs should get fewer job workers when the machine is busy is still open.

## The `unity` CLI

- Tested with `1.0.0-beta.14`, upgraded from beta.13 with `unity upgrade --channel beta`.
- We pin **`1.0.0-beta.14`** or later. Beta.14 stops a command run from a project with no Editor open from reaching another project's Editor, which one-Editor-per-worktree depends on ([04](research/04-unity-cli-pipeline-and-rivals.md)).
- The CLI renames commands between betas. All calls to it go through one module, [`src/upe/unity_cli.py`](src/upe/unity_cli.py), so a rename is a one-place change.
- Each call is aimed at one worktree three ways: the CLI runs with the worktree as its working directory, `UNITY_PROJECT_PATH` is set to it, and the path is passed the way each command takes it, checked with `--help` on beta.14: positional for `open`, `close` and `test`, `--project-path` for `status`, `command` and `pipeline install`. `unity test` starts its own Editor; `open --until-ready` needs the Pipeline package in the project, and `close` without it needs `--force`.

## Measured

On a 16 GB machine, 2026-10-26 ([05](research/05-measurements.md)):

- **Copied `Library`.** A Library copied to a new path imports nothing when it matches the commit. A new path still costs a first open of about 200 s (260 s with three at once), against 20 s for a reopen: Unity rescans the files, recompiles the scripts and reloads the domain. Copying is 118 to 202 s into an empty worktree, and seconds over an earlier copy.
- **Cost of N Editors.** A batch Editor uses 2.2 to 2.5 GB once ready and up to 3.8 GB during a first open. Three at once ran, but filled its memory, with other programs running. CPU stayed at about 43% on average. GUI Editors, PlayMode and builds were not measured.
- **Auth.** No `unity auth login` was needed: the CLI was signed in already (OAuth, keyring), and batch Editors ran under a Personal licence, three at once.
- **Local-only packages.** `unity pipeline install` adds one line to `manifest.json`. Both `com.unity.pipeline` and the embedded `com.upe.agent` get lock entries. Skip-worktree held while Unity rewrote both files.
- **CLI flags.** Settled with `--help` on beta.14 and recorded in `COMMANDS`. The field names inside `data` were read from live runs (`ready.outcome`, `alreadyOpen`, `instances[].state`, `closed`, `method`).

## Not known yet

- **GUI Editors.** What an Editor with a window, in PlayMode or building, costs next to batch ones.
- **A 12-thread, 32 GB machine.** Measured 2026-10-28 ([05](research/05-measurements.md), "Opening a worktree").
  - **A new slot:** 53 to 59 s to make, and a 68 s first open: about 2 minutes, against about 7 on the 16 GB machine.
  - **A reopen:** 11 s alone, 23 to 24 s with three at once.
  - **Three batch Editors at once:** 71 s each for a first open. They used about 3 GB each and peaked at 27.5 of 31.4 GB, with other programs running.
  - **The limit is CPU, not memory:** 90 to 97% with three Editors.
- **Two agents at once.** Tried 2026-10-28 and 29 ([05](research/05-measurements.md), "Two agents at once"). A land takes about 40 to 70 minutes alone and 1 h 50 min with another running, because the full EditMode suite runs on the target and on the merge. A task that loses the race to land repeats its land and its council.
- **Real conflicts.** A scene merge and a conflict have run on the test project ([05](research/05-measurements.md), "Merging real files"). An agent resolved a conflict in a 12 MB scene from the skill alone and it landed ("An agent resolving a conflict").
- **The full scene check's saving.** A land that only adds data assets no longer runs it on the target or the merge: about 21.6 min alone and 42.7 min with two lands at once, from trial logs; no such land has run. A land on a target with a full result kept in the slot its candidate takes spares the target's run: 12.6 min in one trial land, had its candidate been in that slot; in the trials, 0 of the 2 lands on a commit checked in full were in that slot. Neither is measured.
- **Tests under load.** The test project has tests with time limits, which fail when the machine is busy. `test_retries` covers the ones that pass on a second try. The CLI does not re-run parameterised tests; the tool runs their classes once more after a full run, so those no longer stop a land when they pass then (a test that fails only in the suite's order passes then too: see the flow, step 4). How often they fail twice under load is not known.
- **The project's own changes on open.** Whenever Unity opens the project, it rewrites tracked files whose committed versions are older (in the test project, a texture's `.meta`, a package's `Settings.json` and `ShaderGraphSettings.asset`). Until the project commits the upgraded versions, every task shows them as changed outside its claim. Files Unity rewrites with the same content and only new line endings do not count as changes ([05](research/05-measurements.md), "Files Unity rewrites on open").
